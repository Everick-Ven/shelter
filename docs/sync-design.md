# Доски: локальное хранение и синхронизация

Статус: проект этапа 0. Здесь зафиксированы модель данных, границы доверия и формат v1 для последующей реализации. Этот документ не добавляет сетевых вызовов и не меняет существующее хранилище `ss1`.

## 1. Текущая реализация и исходные данные

Проверены `README.md`, `resources/ui/index.html`, `resources/ui/host-bridge.js`, `src/common.h`, `src/browser_app.cc`, `src/clients.cc`, `src/shell_bridge.cc`, `src/shell.cc`, `src/platform.h`, `src/platform_win.cc`, `src/platform_mac.mm` и текущий `src/secret_key.cc`.

### Где находятся доски и задачи

UI открывается как `shelter://app/index.html`. Схема объявлена `standard`, `secure`, `cors` и `fetch`, поэтому у страницы есть origin и постоянный `localStorage`. `BrowserApp::FillSettings` задаёт CEF `root_cache_path` в каталоге пользовательских данных:

- Windows: `%LOCALAPPDATA%\SHELTER`;
- macOS: `~/Library/Application Support/SHELTER`.

Точная внутренняя раскладка Local Storage принадлежит CEF/Chromium; приложению следует считать её частью профиля CEF, а не собственным форматом файла. На диске значения сейчас хранятся **без шифрования**.

`resources/ui/index.html` читает и записывает данные через обёртку `store` над `window.localStorage` (`JSON.parse`/`JSON.stringify`). Основные ключи планировщика:

- `shelter:board` — активная доска;
- `shelter:boards` — реестр досок, список `boards` и активный `id`;
- `shelter:eisenTasks` и `eisenTasks` — распознаваемые legacy-списки задач, которые переносятся в доску.

В объекте доски есть `id`, `name`, `code`, `projects`, `people`, `prios`, `terms`, `formats`, `statuses`, `tasks`, `invites`, `ownerEmail`, а также поля схемы планировщика (`recurrenceRules`, `occurrences`, `taskSchemaVersion` и другие). У задачи встречаются название и описание/комментарий, статус, приоритет, исполнитель, даты, теги, проект, повторы, напоминание и legacy-поля. Нормализатор сохраняет незнакомые поля в `legacy`; миграция обязана сохранять их, а не молча отбрасывать.

Текущий UI уже создаёт plaintext-копии исходных значений в `shelter:planner:migration-backup:*`, `shelter:planner:unreadable-store-backup:*` и `shelter:planner:preimport-backup:*`. Эти ключи также могут содержать задачи. Удаление только `shelter:board` и `shelter:boards` недостаточно.

Текущая миграция планировщика `WP_SCHEMA = 7` сначала делает резервную копию, показывает пользователю предварительный просмотр и лишь затем записывает новую схему. При неудачной проверке записи она старается восстановить исходные строки. Миграция шифрования должна интегрироваться **до** любого такого JS-переноса и не позволять `saveNow()` записывать доски обратно в `localStorage` открытым текстом.

`S.board` и `S.boards` сохраняются напрямую как JSON. Используемый UI для отдельных секретов `ss1` не защищает эти ключи. В этой задаче формат и читатель `ss1` не менять.

В `shelter:lux` хранятся другие данные UI, включая локальные настройки и legacy-данные профиля. Это не источник канонической доски, но его значения и старые email/имена не должны случайно попадать в новый sync-протокол. Поля `ownerEmail`, `invites`, `people` и исполнителей в старой доске считать пользовательскими локальными данными; не использовать их как идентификаторы участников или данные регистрации на сервере.

### Существующие границы безопасности

`UiClient::BridgeHandler::OnQuery` в `src/clients.cc` проверяет ID UI-браузера и текущий URL frame по `shelter://app/`. `Shell::HandleBridge` повторно ограничивает обработчик UI-браузером. Обычная вкладка не должна получать доступ к `shelter://`; это ограничение реализовано в обработчиках навигации. CSP UI содержит `connect-src 'self'` и `worker-src 'none'`. Новые команды должны сохранить эти ограничения: сетевые запросы делает только browser process через CEF URL request API; не добавлять `fetch`/WebSocket из JS и не ослаблять CSP.

Контексты вкладок `persist:space-<key>` и `temp:ghost-<key>` не являются хранилищем досок. Их пути и модель изоляции не менять. Локальная доска принадлежит UI-профилю приложения, а не контексту вкладки.

## 2. Модель угроз и границы гарантий

### Защищаемые данные

- фраза восстановления, derived Ed25519/X25519 secret keys и backup key;
- локальный PIN и защищённая ОС ключевая запись;
- ключи локальных файлов, ключи эпох досок и незашифрованные данные в памяти приложения;
- задачи, заметки, проекты, журнал участников, приглашения и резервные копии;
- bearer-токены API и ciphertext конвертов.

### Противники и гарантии

1. **Сервер, оператор почтового ящика и сетевой наблюдатель.** Не получают фразу, приватные ключи, PIN, ключи досок или plaintext. Сервер видит как минимум публичные ID отправителя/получателя, размер и время конверта, статус подписки, факт общения и IP соединения. Публичный ID псевдонимен, но не скрывает граф связей и временные метаданные.
2. **Потеря устройства/чтение диска другим пользователем.** Локальные файлы досок шифруются отдельным локальным ключом данных; ключ данных оборачивается ключом устройства под защитой DPAPI/Keychain. PIN ограничивает доступ к UI и не является ключом архивов или сетевого шифрования. BitLocker/FileVault остаются дополнительной защитой диска.
3. **Вредоносный код в обычной вкладке.** Не должен получить мост, `shelter://app/`, токены или ключи. Только доверенная UI-страница может вызывать узкие native-методы.
4. **Компрометация UI/renderer или локального процесса пользователя.** Пока приложение открыто, plaintext доски нужен UI для отображения и присутствует в памяти. Native API не должен выдавать приватные ключи в JS; он подписывает/шифрует по команде UI. CSP и проверка моста снижают риск, но не защищают от полного выполнения кода внутри доверенного UI или вредоносного процесса того же OS-пользователя.
5. **Недобросовестный/удалённый участник.** Он может сохранить или экспортировать уже полученные plaintext и старый ключ эпохи. Удаление с чужого устройства — best effort, не отзыв ранее увиденных данных. Защита будущих изменений — новая эпоха; нельзя обещать удалённое криптографическое стирание устройства.
6. **Потеря фразы восстановления.** Сервер не может восстановить фразу или приватные ключи. Если пользователь потерял фразу и все устройства/OS-защищённые копии, восстановление прежнего ID и данных невозможно. Фразу показывать только при создании/восстановлении; не логировать, не класть в Local Storage и не отправлять серверу.

Логи клиента и сервера не должны содержать доски, обновления CRDT, фразы, PIN, ключи, токены, email/имена, тела запросов, URL или пользовательские пути. Ошибки — только категория операции, код результата и корреляционный случайный ID. IP не писать в долговременную БД; для rate limit использовать ограниченное по времени состояние и настроить короткую ретенцию сетевых логов.

## 3. Идентичность, фраза и ключи

### Recovery phrase и публичный ID

Предлагается BIP39 English, 2048 слов: 128 случайных бит от libsodium CSPRNG плюс первые 4 бита SHA-256 как checksum дают 12 слов. Словарь — файл BIP39 `english.txt`, зафиксированный commit `ce1862ac6bcffa1dd20aad858380e51e66e949ea` репозитория `bitcoin/bips`; SHA-256 файла: `2f5eed53a4727b4bf8880d8f3f199efc90e58503646d9ff8eff3a2ed3b24dbda`. Словарь — спецификационные данные, не новая runtime-библиотека. Для первой версии язык слов — English независимо от языка интерфейса.

Из проверенных 16 байт entropy выводить разными HKDF-SHA256 `info` контекстами:

- 32-байтовый seed Ed25519;
- 32-байтовый seed X25519;
- 32-байтовый ключ экспорта/резервных копий.

Далее применять только функции libsodium (`crypto_sign_seed_keypair`, `crypto_kx_seed_keypair`, sealed-box и AEAD API). У libsodium нет отдельного high-level HKDF API: допустима только небольшая композиция RFC 5869 Extract/Expand поверх libsodium HMAC-SHA256 API; SHA/HMAC/Ed25519/X25519 самостоятельно не реализовывать. HKDF label и salt фиксируются версией протокола. Буферы фразы, entropy и secret keys очищать `sodium_memzero` после использования; фраза не попадает в логи, UI telemetry или постоянный файл.

Показывать 12 слов один раз при создании и требовать подтвердить 3 случайные позиции. До подтверждения не завершать создание профиля. Забытую фразу восстановить нельзя; показать это явно до подтверждения.

Публичный ID строить из 32 байт Ed25519 public key в Bech32m: HRP `sh`, версия протокола в data, стандартный checksum Bech32m. ID не содержит email, имени, телефона или server-side internal ID. X25519 public key передавать как часть публичного key bundle для sealed boxes. Изменение Ed25519-ключа означает новую идентичность и новый публичный ID; перенос владения доской оформляется отдельно журналом.

### PIN и локальный ключ

`K_device` — независимый случайный 32-байтовый ключ. Native-слой получает/создаёт его через DPAPI на Windows или Keychain на macOS. Хранилище `src/secret_key.cc` — основа платформенного механизма, но ключ досок должен иметь отдельный purpose/record и не менять `ss1` или его ciphertext. Для macOS текущая реализация в рабочем дереве имеет Keychain и 0600 mirror; такой mirror защищён лишь правами пользователя, поэтому его нельзя считать эквивалентом Keychain. Перед заявлением о защите ключей досок это поведение нужно отдельно проверить и решить, можно ли отказаться от plaintext mirror при стабильной подписи приложения.

PIN — локальный gate перед выдачей доступа UI к данным; он не шифрует экспорт, сетевые сообщения или ключ эпохи. Argon2id из libsodium применять для стойкой проверки локального PIN с отдельной солью и параметрами, подходящими для обеих платформ. PIN не использовать как единственный ключ архивов: короткий PIN не имеет энтропии recovery phrase. После пяти неверных вводов заблокировать PIN-путь и потребовать phrase recovery. Попытки и состояние блокировки хранить native-кодом, не в `localStorage`; UI не получает секретный ключ. Защита от администратора/вредоносного процесса того же OS-пользователя не обещается.

Открытый технический вопрос для этапа 1: определить точную процедуру сброса PIN после recovery phrase и устойчивость счётчика к простому удалению локального файла/переустановке. Это не должно приводить к удалению или замене существующего ключа без явного восстановления.

## 5. Локальное зашифрованное хранилище и миграция

### Новый формат хранения

Хранить доски в native-файлах под `<UserDataDir>/Boards/v1/`, с проверкой каталогов/файлов на symlink/reparse point и атомарной записью через временный файл, flush/fsync и rename. Имя файла — случайный opaque ID; имя доски, задачи, участники и прочая metadata — только внутри ciphertext.

Ключи разделены по назначению:

- `K_device` — случайный ключ устройства под DPAPI/Keychain;
- `K_local` — отдельный случайный ключ локальных файлов профиля/досок, обёрнутый AEAD-ключом, выведенным из `K_device` с versioned domain label;
- `K_epoch` — отдельный случайный ключ синхронизации конкретной доски/эпохи; не использовать его как ключ локального диска;
- `K_backup` — ключ, выводимый из recovery phrase отдельным HKDF context для portable export.

Файл v1: magic/version, opaque board ID, случайный nonce XChaCha20-Poly1305 и ciphertext с tag. В authenticated data включать magic, версию, тип записи и локальный board ID. Сжатие, если понадобится, делать только до шифрования и ограничить размер до распаковки. Не писать plaintext/temp plaintext в файловую систему. Native-код шифрует и расшифровывает данные для UI; приватные identity keys, `K_device`, `K_local`, `K_epoch`, PIN и bearer-token не передавать в JS или `localStorage`.

CRDT materialized document — кэш. Помимо него хранить оригинальные подписанные update-пакеты (зашифрованные локальным ключом), чтобы после изменения журнала можно было пересобрать документ без изменений от отозванного автора. Не заменять этот журнал одной необратимо объединённой Yjs snapshot-версией без происхождения updates.

### Двухфазная миграция существующих ключей

1. До загрузки/нормализации досок UI native-путь определяет legacy-состояние. Пока миграция не завершена, обычный `persist()` не имеет права записывать доску или task backup в `localStorage`.
2. В памяти прочитать исходные строки без потери неизвестных legacy-полей: `shelter:board`, `shelter:boards`, `shelter:eisenTasks`, `eisenTasks`, все `shelter:planner:migration-backup:*`, `shelter:planner:unreadable-store-backup:*`, `shelter:planner:preimport-backup:*` и связанные указатели. Не угадывать по текущей схеме; сохранить полный raw набор и пройти текущую v7-normalization/preview.
3. До преобразования записать **зашифрованный** migration checkpoint, содержащий raw значения, версию, порядок шагов и checksum; flush, прочитать обратно, расшифровать и побайтно сверить. Это резервная копия для rollback, а не новая plaintext-копия.
4. Записать новую зашифрованную модель доски, прочитать обратно, расшифровать, валидировать все доски/задачи и сверить количество/ID/legacy fields. Сохранить migration state-machine marker так, чтобы следующий запуск мог продолжить или откатить.
5. Только после проверки убрать старые ключи досок и все их plaintext backup-ключи. Если любое чтение, запись или проверка не удалась — не удалять исходник, не показывать пустую доску как успешный результат, перейти в read-only режим и предложить восстановление/экспорт из encrypted checkpoint.
6. Повторный запуск обязан быть идемпотентным. Проверить точки crash/failure между каждым шагом и автоматический rollback; не генерировать новый `K_device`/`K_local` поверх существующего неразбираемого key record.

**Критическое ограничение Local Storage:** удаление `localStorage` key не доказывает, что старая строка удалена из LevelDB WAL/SST-файлов и не оставляет остаточных копий. Чтобы заявлять «plaintext досок больше нет на диске», надо проверить на CEF 154 очистку origin storage/профиля и, при необходимости, после создания зашифрованного checkpoint ротировать/пересоздать хранилище UI origin, восстановив из encrypted checkpoint только разрешённые несекретные настройки. Не считать `removeItem()` или перезапись secure wipe. На SSD/APFS/NTFS программное удаление не гарантирует физического стирания; для этого нужны штатное полнодисковое шифрование и политика ОС. Проверка Local Storage cleanup и crash recovery — блокирующая перед этапом 1.

## 6. CRDT-документ, updates и конверты

### Модель Yjs

Один `Y.Doc` на доску, namespace/board ID — случайный идентификатор, не email и не имя. Предлагаемая структура: `Y.Map` для board metadata/config; `Y.Map` задач по стабильному task ID; `Y.Array` порядка ID задач; отдельные map/array для projects, recurrence rules и occurrences. Поля описания — plain text; UI продолжает экранировать пользовательский текст при отображении. Текущая модель `S.board` остаётся view-model и сериализуется в/из Yjs model через проверенный адаптер.

Не посылать полные JSON-доски при каждом изменении. Один локальный Yjs update — отдельная единица происхождения, подписи и replay. Не объединять в один подписанный пакет updates разных авторов. Дубликат одного update безвреден для Yjs, но update проверяется и авторизуется **до** `Y.applyUpdate`.

Yjs не проверяет права. Авторский Ed25519 key должен быть связан с Yjs client ID; конфликт/подмена уже объявленного client ID отклоняется. Нельзя применять update, который маскирует несколько авторов под подпись одного. Это требуется закрепить тестом до использования Yjs snapshots/compact.

### Обычный sync envelope v1

Все поля ниже — binary, с фиксированным порядком и big-endian длинами; не подписывать произвольную JSON-сериализацию. На внешнем слое — только версия, nonce и ciphertext, чтобы сервер не видел board ID, epoch, автора и содержимое:

```text
outer = magic("SHBE") || version(u8=1) || nonce(24) || ciphertext_and_tag
ciphertext_and_tag = XChaCha20-Poly1305(K_epoch, plaintext, AAD="SHELTER-MAILBOX-ENVELOPE-v1")
```

Внутри plaintext — канонический signed update:

```text
magic("SHBU") || version(u8=1) || board_id(32) || epoch(u64) ||
packet_id(16 random) || author_ed25519_public(32) ||
client_id(u64) || update_length(u32) || yjs_update || signature(64)
```

`signature = Ed25519("SHELTER-BOARD-UPDATE-v1" || все предыдущие поля, включая yjs_update)`.

При получении: проверить AEAD, формат/размер, журнал участников, текущую роль и epoch, подпись автора и привязку `client_id`; только потом записать зашифрованный оригинальный пакет в локальный operation log и применить update. Повтор того же `packet_id`/hash идемпотентен; тот же ID с другим hash — ошибка и не применяется. Сервер принимает opaque bytes и не может подтвердить подпись/расшифровать их.

Идентификаторы, client IDs, packet IDs, nonce и board IDs генерировать через libsodium CSPRNG; не использовать `Math.random()` для криптографически значимых значений. Размеры ограничивать до выделения больших буферов. Серверные лимиты применяются к ciphertext bytes, не к plaintext.

### Снимки и удаление автора из CRDT

Полученный Yjs update может быть применён, пока локальный клиент ещё не видел подписанную запись об удалении. Поэтому хранить encrypted журнал отдельных подписанных updates, не только текущую Y.Doc. При получении нового membership journal пересобрать materialized Y.Doc из разрешённых авторов и updates; исключить операции всех удалённых участников независимо от того, когда они были созданы или попали в mailbox.

Пригласительный snapshot и последующая компактизация не должны скрывать происхождение updates. В первой реализации безопаснее передавать набор исходных подписанных updates (или checkpoint с проверяемой per-author provenance), чем монолитный snapshot, подписанный владельцем и не позволяющий клиенту проверить вклад удалённых участников. Крупные snapshot при необходимости делить на подписанные chunks с общим random transfer ID, порядком, количеством и hash итогового ciphertext. Формат checkpoint/компактизации остаётся блокирующим вопросом этапа 4.

## 7. Журнал участников и роли

Журнал — последовательность owner-signed бинарных записей, зашифрованная для участников. Каждая запись содержит domain/version, `board_id`, строго возрастающий `seq`, hash предыдущей записи, тип события, текущий owner public ID, subject/member public ID, роль, номер эпохи и типизированные данные события. Signature Ed25519 владельца покрывает всё содержимое; hash записи считается libsodium `crypto_generichash` от payload и signature. Не использовать время клиента как основание для прав.

События v1:

- `invite`: новый member Ed25519/X25519 public bundle, роль `writer`, invite nonce и текущие `journal_hash`/epoch;
- `remove`: member ID отзывается начиная с текущей записи;
- `rotate_epoch`: новый номер эпохи, причина и ссылки на key envelopes; сам новый ключ только в адресных зашифрованных пакетах;
- `transfer_owner`: новый owner ID и checkpoint журнала. Текущий владелец подписывает передачу; новый владелец подтверждает её своей подписью, затем только он подписывает следующие события.

Роли на сейчас: `owner` и `writer`. Значение `reader` зарезервировать в кодировке, но не выдавать и не показывать в UI. Право записи проверять по наиболее свежей валидной цепочке журнала до применения update.

Проверки клиента:

- начинать от owner key, закреплённого при приглашении, и проверить весь hash chain/transfer chain либо owner-signed checkpoint;
- повтор уже принятой `seq` и того же hash — игнорировать; пропуск seq — запросить недостающий журнал; тот же seq с другим hash — fork, остановить применение и запросить восстановление;
- отклонить неверную подпись, неправильный `prev_hash`, изменение журнала не текущим владельцем, роль без права записи и update удалённого участника;
- хранить high-water `seq`/hash native-кодом под защитой устройства, чтобы сервер не мог незаметно откатить локально виденное состояние;
- при старте обработать новые control/journal messages до CRDT updates, затем пересобрать документ по актуальному составу.

Несколько устройств с одной phrase дают одну owner identity. Параллельное создание двух записей с одинаковым `seq` может дать fork; сериализация owner-журнала и восстановление после fork — открытый вопрос. До решения нельзя молча выбирать одну ветку.

## 8. Приглашение, почтовый ящик и удаление

### Приглашение

Owner создаёт криптографически случайный одноразовый secret и срок действия; ссылка/QR содержит owner public ID и этот secret, но не board title, email или имя. Secret не писать в логи/URL telemetry, использовать ровно один раз и удалить после истечения/принятия. Приглашённый сначала создаёт свою identity и показывает свой публичный ID владельцу.

После принятия обе стороны получают одинаковый короткий fingerprint из `crypto_generichash` от domain label, board ID, owner ID, invitee ID и invite nonce; сверяют его по независимому каналу до принятия. Затем владелец отправляет актуальный журнал и snapshot/набор подписанных updates; epoch key для нового X25519 public key — в `crypto_box_seal` пакете, подписанном owner Ed25519. Перед подтверждением явно показать: «Владелец может убрать эту доску с вашего устройства. Удаление сработает, только если ваше приложение получит запрос».

### Bootstrap/key distribution

Обычные board updates шифруются ключом эпохи и подписываются автором, как выше. Получатель ещё не знает epoch key при первом приглашении, а новый key не может быть зашифрован тем ключом, который он доставляет. Поэтому invite/bootstrap, передачу epoch key и адресный запрос удаления оформлять как owner-signed `crypto_box_seal` control package для X25519 public key получателя. Snapshot/updates внутри него всё равно остаются XChaCha20-Poly1305-зашифрованными. Для rekey существующих участников пакет дополнительно может быть закрыт текущей эпохой; для нового приглашения и запроса удалённому участнику sealed box — необходимое исключение из symmetric-epoch транспорта.

### Серверный mailbox (этап 3)

Внешний HTTP API вызывается только из C++ (`CefURLRequest` или эквивалент), через узкие UI bridge methods. Не добавлять универсальный JS network proxy. Предлагаемые операции:

- регистрация публичного key bundle, с proof-of-possession подписью;
- одноразовый challenge и вход подписью Ed25519; подпись связывает случайный challenge, ID, назначение и срок действия; challenge одноразовый и короткоживущий;
- `POST` opaque envelope получателю по public ID;
- `GET` только собственного mailbox и `POST` подтверждения конкретного полученного envelope;
- статус подписки по public ID.

Bearer-токены хранить только в памяти на время сессии или в DPAPI/Keychain; не писать в `localStorage`, URL, HTTP body logs или сообщения UI. Challenge, nonce, токен и регистрацию публичного ключа привязывать к фиксированной версии API и HTTPS origin.

Mailbox хранит только необходимые opaque поля: случайный envelope ID, sender/recipient public IDs, ciphertext BLOB, created/expires timestamp, ciphertext size и статус доставки. Временное хранение до ack, TTL по умолчанию 30 дней с серверной настройкой, удаление по ack или TTL. Не хранить board ID, текст задач, member list, private key, email или имя. Сервер видит sender/recipient IDs и метаданные трафика. Применять rate limit по sender identity и краткоживущий IP bucket; не сохранять полный IP в бизнес-таблицах.

Транспортный API предпочтительно передаёт envelope как `application/octet-stream`, чтобы не добавлять JSON/base64 копии крупных payload. Ack выполнять только после durable local save либо после окончательного отклонения некорректного сообщения. Ack повторяемый и идемпотентный. Точные max body, batch size, квоты и rate-limit значения выбрать после измерения реальных досок; хранить их в server config. До этого не принимать неограниченные тела.

## 9. Вывод участника и смена эпохи

Владелец подписывает `remove`, увеличивает epoch и генерирует новый независимый `K_epoch`. Оставшимся участникам рассылаются адресные sealed boxes с новым ключом и новым журналом; удалённому участнику ключ новой эпохи не отправляется. Все последующие пакеты используют новую эпоху. Каждая установка сверяет состав с полученными подписанными записями при старте и перед синхронизацией.

Отдельно отправить удалённому участнику owner-signed sealed-box запрос удаления, привязанный к board ID, журналу/seq, owner key и сроку. Клиент сверяет владельца с ключом из принятого приглашения и всей цепочкой передачи владения, предлагает экспорт, удаляет локальный ciphertext, ключи эпох и operation log, затем подтверждает доставку. Если сообщение не доставлено или приложение не запущено, удаление не гарантируется. Интерфейс не обещает обратного.

У клиента, который ещё не получил актуальную запись журнала, может быть устаревшее локальное представление. Поэтому сохранять подписанные updates отдельно и пересобирать Y.Doc после получения нового журнала. Не применять обновления, подписанные уже удалённым ID; если такие изменения ранее попали в materialized state на устаревшем roster, убрать их при rebuild. Удаление существующих копий plaintext на чужом устройстве криптографически гарантировать нельзя.

## 10. Экспорт, импорт и автокопии

Portable archive версии v1 — бинарный файл с magic/version, случайным nonce и XChaCha20-Poly1305 ciphertext, authenticated data содержит формат и версию. Ключ — `K_backup`, выведенный из той же phrase через отдельный HKDF context. Внутри — identity public bundle, локальные доски, подписанные журналы/updates, необходимые board epoch keys и schema versions; не помещать в archive plaintext фразу. На новом устройстве phrase восстанавливает тот же ID; создаются новые `K_device`/`K_local`, содержимое переносится и шифруется заново. Подписка не считается действительной по полю в архиве: импорт обязан повторно запросить сервер по public ID; при ошибке/неизвестном ответе — fail closed.

Ручной export и automatic folder backup сначала шифруют весь архив до записи; не создавать незащищённые временные zip/JSON. Пользователь выбирает каталог через native picker. Автокопия не вызывает API облачных дисков: синхронизацию выполняет файловый клиент пользователя. Ротация хранит последние N полностью записанных архивов; использовать атомарную запись, не логировать путь и не удалять предыдущую копию до проверки новой.

Открытые параметры: N, периодичность, поведение при нехватке места, максимальный размер архива и UX подтверждения phrase при восстановлении.

## 11. Подписка и ограничения server-side

Premium status принадлежит public ID, не email. Интерфейс провайдера оплаты оставить абстракцией; настоящий checkout/status считать закрытым, пока серверная проверка и интеграция не настроены. Не доверять локальным полям `premium`, trial, order или старому account state. Любой timeout, ошибка TLS/сервера или неизвестный ответ означает `not premium`; никакой offline grace period не включать без отдельного решения.

Так как сервер не видит board ID/содержимое, он не может честно лимитировать число досок или задачи. Рекомендуемая первая модель: квота ciphertext bytes/сутки или в месяц на **отправителя** (разная для free/premium) плюс абсолютный cap размера очереди и частоты на **получателя** против спама. Считать bytes и requests по public ID, не анализировать содержимое. Конкретные значения, период сброса и наличие recipient quota — открытые продуктовые параметры; нельзя делать вид, что сервер применяет premium-квоту, пока backend не включён.

## 12. Тесты и приёмка по этапам

### Этап 0 — этот документ

- сверить карту Local Storage с фактическими ключами UI и legacy migrations;
- проверить, что документ фиксирует риски plaintext LevelDB и не обещает физическое стирание SSD;
- проверить ссылки, версии и хэши зависимостей; код приложения не меняется.

### Этап 1 — identity, PIN, локальные доски

- BIP39 официальные vectors; RFC 5869 HKDF vectors; один фиксированный 12-словный test phrase с ожидаемыми Ed25519 public ID, X25519 public key и backup key; одни и те же bytes на Windows x64/macOS Intel;
- libsodium Argon2id/PIN tests; пять неверных PIN, блокировка PIN и восстановление phrase; restart не сбрасывает состояние;
- round-trip local AEAD, неверный tag/key/version, truncation/oversize, atomic write/readback;
- migration tests для каждой группы legacy keys, backup verification, quota/permissions failure, повреждённого JSON и crash после каждого шага; точное восстановление исходных значений при rollback;
- после успешной миграции проверить отсутствие живых plaintext ключей/backup и CEF Local Storage remnants; проверить режим read-only на ошибке;
- sentinel phrase/PIN/key/board text не встречается в логах и файлах открытым текстом (кроме памяти приложения во время unlock).

### Этап 2 — export/import/автокопия

- фиксированные archive vectors, wrong phrase/tag, повреждение/truncation/oversize;
- import на чистый профиль возвращает тот же public ID, boards/journal, но перепроверяет subscription online;
- отказ записи новой копии не удаляет старую; ротация N; отсутствие plaintext temp-файлов; пути не появляются в логах.

### Этап 3 — server MVP

- вход Ed25519 challenge, одноразовость challenge, expiry и replay rejection;
- аккаунт A не читает/ack-ает mailbox B; ack идемпотентен;
- size/rate cap, TTL 30 дней/config override, удаление после ack, истечение;
- SQLite/Postgres тестовая конфигурация, Dockerfile и отдельный CI; логи проверяются на отсутствие тел, phrase, ключей, PIN и долгоживущих IP.

### Этап 4 — sync/CRDT/invite/journal

- Yjs документ сходится при перестановке и дублировании подписанных updates;
- несколько независимых авторов с concurrent edits, удаление/reorder, повторная сборка после revocation;
- неправильная Ed25519 подпись, forged/повторный client ID, поддельная запись об удалении, replay старой записи, gap/fork, запрещённая роль;
- update удалённого участника, созданный офлайн до получения уведомления, должен отбрасываться и не попадать в пересобранную Y.Doc;
- нельзя принять snapshot без проверяемой provenance после удаления участника;
- invite token one-time/expired/replay, одинаковый fingerprint на двух клиентах, epoch key недоступен неучастнику.

### Этап 5 — удаление/epoch rotation

- подписанная запись удаления и цепочка; неверный owner key/старый journal не удаляет данные;
- новый epoch key получают только оставшиеся ID; старый ключ не открывает новые updates;
- delete request ждёт ack/TTL, UI предлагает export, получатель проверяет pinned owner/transfer chain;
- offline/неполучивший запрос клиент не объявляется удалённым; best-effort текст остаётся точным.

Все Windows/macOS нативные тесты и release builds запускать только GitHub Actions. Нельзя выдавать успешный JS-тест или статический просмотр за проверенную нативную сборку или ручной тест ОС.

## 13. Открытые вопросы и риски

1. **Local Storage / LevelDB cleanup (высокий риск, блокирует этап 1):** можно ли на CEF 154 надёжно удалить весь origin store после encrypted checkpoint и восстановить остальные UI-настройки без plaintext remnants? Нужен Windows/macOS эксперимент. `localStorage.removeItem` недостаточно.
2. **Yjs authorship и compaction (высокий риск, блокирует этап 4):** формат per-author updates, binding Yjs client IDs к identity/device, перенос snapshot с provenance, rebuild/compaction и стоимость хранения журнала. Монолитный Yjs snapshot не доказывает автора внутренних изменений.
3. **Recovery phrase:** English BIP39 выбран для v1; нужно утвердить UX локализации фразы, повторное подтверждение при импорте и порядок операций при забытой phrase. Саму phrase восстановить нельзя.
4. **PIN:** минимальная длина, параметры Argon2id, возможность смены PIN и устойчивость lockout counter к сбросу профиля/переустановке.
5. **OS key storage:** Keychain ACL и plaintext mirror на текущей macOS реализации; стабильная подпись приложения и совместимость обновлений/переноса профиля.
6. **Server:** выбрать Go или Node, SQLite или PostgreSQL MVP, hosting/TLS/domain, exact payload/rate quotas и IP log retention. Предварительная рекомендация — Go + SQLite для небольшого самостоятельного сервиса; подтвердить нагрузочными/эксплуатационными требованиями, не вводить пока как факт.
7. **Premium:** точные free/premium quotas; рекомендуются sender byte quota и recipient queue cap, но числа и расчётный период не заданы.
8. **Owner multi-device/forks:** одна phrase даёт общий owner key; параллельные офлайн owner-журналы требуют явного разрешения fork, нельзя выбрать одну версию автоматически.
9. **Legacy персональные поля:** `ownerEmail`, email-приглашения и имена внутри локальных записей должны остаться только локальными/зашифрованными либо быть явно преобразованы. Новые invite/server API используют только public IDs.
10. **Mailbox bootstrap exceptions:** обычный sync идёт под `K_epoch`; начальное распределение ключа и запрос на удаление используют sealed boxes, поскольку получатель не владеет соответствующей эпохой. Это криптографически необходимо; формат control envelope закрепить отдельными interoperability vectors.
11. **Размеры/retention:** установить max envelope, chunk size, batch size и квоты после измерения реальных board exports; сервер не принимает неограниченные данные.

### Итоговая оценка рисков

- **Высокие:** потеря/утечка recovery phrase; остатки plaintext Local Storage после миграции; недоказуемое происхождение данных в сжатом CRDT snapshot; невозможность удалённо стереть уже скопированные данные у участника.
- **Средние:** metadata/граф связей, видимые mailbox-серверу; fork owner-журнала при нескольких offline устройствах; атаки same-user malware при разблокированном приложении; неверно выбранные server quotas.
- **Управляемые:** replay, подмена сообщения и изменение membership журнала при соблюдении подписанных форматов, проверке цепочки, epoch rotation и наличии тестов на обеих платформах.
